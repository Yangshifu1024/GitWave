# fix: 更新清单里的下载地址改为普通下载地址

> 本文作废 `docs/tasks/fix-ci-redundant-publish-job/plan.md:25` 的一条结论：那里写「清单 URL 为 `api.github.com/.../assets/<id>` 形态，release 转正后 updater 可用」，实测这个形态在请求缺 User-Agent 请求头或接口额度耗尽时会返回 403，故该结论不再成立。

## 一、问题

用户反馈：应用内点更新失败，报 403。

核实 v0.9.2 已发布的 `latest.json`：8 个平台的下载地址全部是 GitHub 的接口地址。

```
"darwin-aarch64": {
  "url": "https://api.github.com/repos/Yangshifu1024/GitWave/releases/assets/574424477",
  ...
}
```

实测（2026-09-19，本机，未登录）：

| 请求 | 结果 |
|---|---|
| 接口地址，不带 User-Agent 请求头 | **403** `Request forbidden by administrative rules` |
| 接口地址，带请求头 | 302 跳转到下载服务器 |
| 普通下载地址 `github.com/<仓库>/releases/download/<标签>/<文件>`，不带请求头 | 200 |

接口地址有两个坑：

1. 请求头缺失直接返回 403；
2. 它按 GitHub 接口调用次数计数（未登录按 IP 每小时 60 次），额度用完同样返回 403。每台已安装的机器每次更新都要消耗一次，用户量或检查次数一上来就会踩到。

普通下载地址走的是下载服务器，两个坑都不存在，GitHub 发布页上的下载按钮用的也是这种地址。

## 二、改动

| 文件 | 改动 |
|---|---|
| `.github/workflows/build.yml` | 新增任务 `rewrite-manifest-urls`，在三个平台的构建任务全部成功后运行：下载 `latest.json` → 用该发布自身的附件列表建立「附件编号 → 附件下载地址」对应 → 替换 `platforms.*.url` → 覆盖上传 |
| 已发布的 v0.9.2 的 `latest.json` | 用同一套逻辑改写后重新上传（版本号与标签不动），已安装用户立刻能正常更新 |
| `.agents/skills/gitwave-release/SKILL.md` | 发布前核对项补一条：清单里的地址必须是普通下载地址 |
| `README.md` | 持续集成说明补一句 |
| `docs/tech/engineering/00-overview.md` | 发布流程概述补一条「更新清单」 |

任务里的两道断言（任一不满足就报错停止，不会把不能用的清单传上去）：

1. 每个平台的地址都必须以 `https://github.com/` 开头——接口地址不满足，其它域名也不满足；
2. 三个主平台键 `darwin-aarch64` / `linux-x86_64` / `windows-x86_64` 必须齐全——某个平台在清单合并窗口里丢掉，意味着那个平台的用户会静默地再也收不到更新。

**为什么文件名与地址都从附件列表直接取**：改写的输入只用该发布自己的附件信息（附件编号 + 附件下载地址），既不对安装包命名做假设，也不自己拼地址，标签里含 `/`、文件名含空格等情况都不会出错。历史上的自研清单生成器正是因为对附件命名做了假设而出错并被删除（见 `docs/tasks/fix-ci-redundant-publish-job/plan.md`），这次不重复同一个错误。

**为什么不改应用代码**：旧版本的更新通道已经发出去了，改代码只对以后新装的用户生效，而更新失败的用户恰恰升不上来。清单在服务端，改它立刻生效。

**为什么沿用原清单而不是另写一份**：`docs/tasks/fix-ci-redundant-publish-job/plan.md` 当时的决策是「清单只由构建工具生产，避免两套生产逻辑并存」。本次是有意开的例外，边界写清楚：只替换 `platforms.*.url` 一个字段，版本号、更新说明、发布时间、各平台签名一律不动（已用真实清单逐键比对确认）。其余字段仍由构建工具唯一生产。

### 已知限制

- 构建工具在每次构建任务结束时都会重写清单。以后如果只重跑某一个失败的构建任务（而不是整条流水线），清单会再次出现接口地址，且本任务不会被执行；此时只能靠发布前的人工核对（已写进 `.agents/skills/gitwave-release/SKILL.md`）兜底，或整条流水线重跑。
- 覆盖上传属于先删后传，如果上传中途失败，草稿发布上可能短时间没有 `latest.json`。此时任务本身是红灯，发布前的人工核对同样能拦住。

## 三、验证

1. 把工作流里的脚本原样抽出来干跑，用替身 `gh` 控制输入，覆盖五种情况（`jq` 与两道断言都是真的）：

| 用例 | 期望 | 实测 |
|---|---|---|
| 接口地址的清单（v0.9.2 修复前的形态） | 改写成普通地址并上传 | 退出码 0，上传一次，8 个地址全部改写 |
| 已经是普通地址的清单 | 幂等通过 | 退出码 0 |
| 有一个地址指向 `example.com` | 拒绝上传 | 退出码 1，报「1 platform URL(s) that are not github.com download links」 |
| 少一个主平台键 | 拒绝上传 | 退出码 1，报「missing darwin-aarch64 / linux-x86_64 / windows-x86_64」 |
| 附件列表为空、清单仍是接口地址 | 拒绝上传 | 退出码 1，报「8 platform URL(s)…」 |

2. 第一个用例的改写结果与线上已修复的清单逐键比对完全一致——版本号、更新说明、发布时间、8 个签名均未变动。
3. `.github/workflows/build.yml` 通过 YAML 解析（5 个任务、`needs`、job 级权限、步骤均符合预期），显式指定文件路径时通过 prettier 检查（注意仓库的 `.prettierignore` 排除了 `*.yml`，全量格式检查不覆盖工作流文件）。
4. 重新上传后再次下载核对：`version=0.9.2`，指向接口域名的地址 0 个，普通下载地址 8 个。
5. 8 个地址逐个取首字节验证：全部返回 206。第一次检查有 3 个地址超时，重试后全部成功，属本机网络到下载服务器的波动，与地址本身无关。
6. 应用读取清单的入口地址（`releases/latest/download/latest.json`）已返回改写后的内容。

## 四、非目标

- 不改应用代码（原因见上）。
- 不移动 v0.9.2 的标签，不新增版本号。
- 不做「清单内容生成」：平台键、签名、更新说明仍全部由构建工具生产，本任务只替换地址字段。
