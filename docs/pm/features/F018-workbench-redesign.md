# F018 · GitWave 工作台与界面语言重设计

## 背景

用户要求完整审视现有代码、界面和交互，再提出全局重构方案。现有 History 主画布、窄 Inspector 与多套任务弹窗需要一起评估。目标用户暂按日常处理多仓库、branch、diff、stash、worktree 的开发者设定；尚未进行外部用户访谈。

## 提议方案

推荐「GitWave 工作台」：保留 Workspace → repository 的稳定上下文，History 与 Changes 成为同级主模式；复杂审阅进入主画布；AI 在当前任务内提供可审阅的协作结果。

- [完整设计草案](../../design/09-workbench-redesign.md)：现状证据、备选方向、信息架构、视觉语言、全模块交互和验收。
- [工程计划](../../tasks/feat-workbench-redesign/plan.md)：模块迁移、状态隔离、分期和验证。

## 用户故事与优先级

| 优先级 | 用户故事 | 验收标准 |
|---|---|---|
| P0 | 作为开发者，我希望同时明确当前仓库、HEAD 和正在审阅的对象 | 三者有独立标识；操作进度不替换仓库身份；选择 commit 不 checkout |
| P0 | 我希望审阅、stage、编写 message 和 commit 在主工作区完成 | Changes 是一级入口；切 History 再返回不丢草稿与选择；commit 不自动 push |
| P0 | 我希望读代码时有足够宽度，也能保留历史上下文 | History 默认上下布局；详情内文件列表与 diff 分开；可专注 diff 并返回原位置 |
| P0 | 我希望理解冲突处理进行到哪一步 | 文件编辑、标记解决、完成 Git 操作有独立状态；未保存缓冲受到保护 |
| P1 | 我希望 stash、恢复、仓库工具遵循一致的导航 | 完整能力有新旧入口映射；复杂详情进入主画布；危险动作明确对象与后果 |
| P1 | 我希望快速找命令且清楚何时调用 AI | 本地命令优先；Ask AI 显式触发；显示作用范围与 provider；无自动写 Git |
| P1 | 我希望知道设置作用于哪里 | 应用与 Workspace 设置明确区分；保留已有隐私、网络、字体、双语与主题能力 |
| P2 | 我希望调整阅读密度和布局 | 核心流程验证后再引入额外偏好与空间化拓扑实验 |

P0 覆盖最高频或最高风险旅程，P1 完成全产品一致性，P2 在核心收益得到验证后再投入。全产品重设计是最终范围，分期不代表删除低频 Git 能力。

## 衡量

先记录当前版本基线，再用相同测试仓库进行 5–8 名目标开发者的形成性测试。目标：核心任务无协助成功率 ≥90%；审阅→stage→commit 的完成时间中位数较基线降低 20%。这些是待验证目标，不是已获得结果。默认不新增遥测，采用本机观察记录。小样本结果仅用于发现问题，不能宣称统计显著。

## 影响

- 涉及模块：应用壳层、Workspace/repo 导航、History/diff、Changes、整合与冲突、stash、恢复、AI、设置及仓库工具。
- 影响版本：待定，不在本阶段 bump version。
- 兼容性：保持 Workspace 数据与仓库内容兼容；导航习惯有变化，需要迁移提示；旧布局偏好需有版本化迁移。
- 原则：本地优先、单 active repo、完整 Git 能力、中英双语；AI 不自动 commit / push / merge。
- 非本提案承诺：PR 平台集成、全仓 file tree、hunk/line staging、vim mode、远端协作服务。
