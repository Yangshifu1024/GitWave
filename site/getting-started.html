Getting started

From an empty window to your first push

GitWave is a visual Git client. This tour shows you the parts of the window you will touch every day, and the four actions that take a repository from your disk to your remote.

About 10 minutes · macOS, Windows and Linux

1 · Workspaces and repositories 2 · The window, pane by pane 3 · The main path in four steps 4 · Cloning a remote repository 5 · When something gets in the way

Workspaces and repositories

A workspace is not a folder on your disk. It is an abstract group that holds the repositories you work on together — a backend and a frontend, three versions of the same library, or a repository and its submodules. Nothing on the filesystem ties those repositories to each other.

Switch between workspaces with the selector at the left end of the title bar. Inside a workspace every repository is a tab: click a tab to make that repository active, drag tabs to reorder them, and scroll the tab strip with the mouse wheel when it overflows. The active tab is always kept in view.

Everything you see belongs to the active repository — the commit graph, the sidebar, the working copy, the AI context. Switching tabs switches all of it at once.

You can add several repositories at once. Duplicates and unusable paths are reported one by one, and the rest of the batch still goes through.

The window, pane by pane

The title bar carries the app menu, the workspace selector, the sync actions (fetch, pull, push) and the Changes button that opens the working-copy window.

  • Left sidebar — collapsible groups for branches, tags, stashes, remotes, submodules and worktrees, plus the working-copy entry. It auto-expands to the branch you check out.
  • Middle — the commit history graph: one row per commit, drawn in the fork style so merges and parallel lines stay readable while you scroll. Right-click a commit for checkout, cherry-pick, revert, reset and more.
  • Right — the inspector for the selected commit: its message, its author and the list of files it touched. Click a file to read its diff.

The main path in four steps

These four steps are the everyday loop: bring a repository in, read a commit, commit your changes, push.

  1. 1

    Add a repository

    While the main area is empty, GitWave shows three buttons: Clone remote repo, Initialize new repo and Add existing local repo. Pick Add existing local repo, select the folder that already contains a .git directory, and the repository opens as a tab. You can select several folders in one go.

    The same three actions live in the app menu under Repository. On macOS that menu is in the system menu bar; on Windows and Linux it is the menu bar at the top of the window.

  2. 2

    Read a commit

    Click any row in the history graph. The inspector on the right fills with that commit's message, its author and its changed files; click a file to open its diff. Switch between side-by-side and unified views, and use the per-hunk actions when you want to deal with a single hunk of a file instead of the whole thing.

  3. 3

    Commit your changes

    Edit your files in whatever editor you already use — GitWave refreshes the working copy as files change. The Changes button in the title bar opens the working-copy window, where unstaged and staged files are listed separately: stage what belongs in this commit, write the message, and press Commit.

    Conventional-commit type chips (feat, fix, docs, …) prefix the message for you, and the Generate button drafts a message from the staged diff once you have configured a provider key.

  4. 4

    Push

    The push button in the title bar opens a confirmation. It takes three things: the target remote, whether to push the tags on this commit, and whether to force. Check the remote and the branch it pushes to, then confirm. The dialog never sets the upstream — if this branch has no upstream yet, right-click the branch in the left sidebar and choose Tracking… to pick the remote branch it should track. Fetch and pull sit next to the push button.

Cloning a remote repository

Cloning is the other way to get a repository in. Use Clone remote repo in the empty main area, or the same entry in the app menu under Repository. Paste the remote URL and choose the local directory; GitWave fetches the repository and opens it as a tab. The URL field takes HTTPS and SSH addresses alike, and the remote's default branch is checked out.

HTTPS. The first operation that needs credentials — usually the first push or fetch — opens a sign-in window inside the app. What you type there is handed to your system credential manager (Keychain on macOS, Credential Manager on Windows, libsecret on Linux), so later operations do not ask again.

SSH. If the remote URL starts with git@, GitWave uses the keys your ssh-agent holds — the same ones the git command line uses. Open Settings → SSH Keys to see them; Add SSH key registers another private key. Use Test SSH connection to check a key against a host before you push.

When something gets in the way

Five things that stop people on the first day, and where to fix them.

An empty repository has nothing to commit

A repository you have just initialised has no commits and no files yet, so the commit graph shows the Create first commit button instead of a history. Clicking it opens a dialog titled This repository is empty, which explains why there is nothing to commit and offers Clone remote repo to bring an existing project in. To make the first commit yourself, put files in the working directory, then open the working-copy window and commit them.

The sign-in window keeps coming back

GitWave saves HTTPS credentials through your system credential manager. If the prompt reappears on every push, the credential was never stored — enter it once more and make sure the credential manager is unlocked and running.

SSH asks for a passphrase, or the push is rejected

Open Settings → SSH Keys. That panel lists the keys in your ssh-agent, Add SSH key registers another private key, and Test SSH connection talks to a host without touching your repository. A rejected push over a git@ URL usually means the host does not have your public key yet. A key with a passphrase cannot be added here — run ssh-add in a terminal first.

A merge or rebase stops on a conflict

Conflicted files show up in the working copy and in the Merge conflicts panel. Open a file there, compare both sides, and choose which side to keep file by file — then continue the merge or rebase from the same panel.

The interface language

Settings → General switches the interface between English and 中文. The screenshots in this guide are in the language of the page you are reading, so switch the app language first if your window does not look like the pictures.
